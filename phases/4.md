# Phase 4: QuerySet Engine

## Goal
Implement the full Django-equivalent `QuerySet` — lazy, chainable, async-first. Every method that returns data is a Python awaitable. Chaining methods (filter, exclude, order_by, etc.) returns a new `QuerySet` without touching the database. The actual SQL is built and executed only when the queryset is "evaluated" (awaited, iterated, or explicitly evaluated).

## Scope
- `QuerySet` struct in Rust with a `QueryState` builder
- Full filter/exclude system with `Q` object support and field lookups (`__exact`, `__icontains`, `__in`, `__gt`, etc.)
- All read methods: `all`, `get`, `first`, `last`, `earliest`, `latest`, `exists`, `count`
- All write methods: `create`, `get_or_create`, `update_or_create`, `update`, `delete`
- Projection: `values`, `values_list`, `only`, `defer`
- Aggregation: `annotate`, `aggregate` with built-in functions (Count, Sum, Avg, Max, Min)
- Joins: `select_related`, `prefetch_related`
- Ordering: `order_by`, `reverse`, `distinct`
- Slicing via `__getitem__` (returns new QuerySet or awaitable for single item)
- Raw SQL: `raw(sql, params)`
- Iteration: `__aiter__` (async for)

## QueryState Rust Struct

```rust
pub struct QueryState {
    pub model_name: String,
    pub database: Option<String>,          // using()
    pub filters: Vec<FilterNode>,          // accumulated WHERE conditions
    pub excludes: Vec<FilterNode>,         // negated conditions
    pub order_by: Vec<OrderExpr>,
    pub distinct: bool,
    pub select_fields: SelectFields,       // All | Only(Vec<String>) | Defer(Vec<String>)
    pub annotations: Vec<Annotation>,
    pub select_related: SelectRelated,
    pub prefetch_related: Vec<String>,
    pub limit: Option<u64>,
    pub offset: Option<u64>,
    pub result_type: ResultType,           // Models | Values | ValuesList | FlatList
    pub extra_select: Vec<(String, RawExpr)>,
}
```

All `QuerySet` methods that return a new `QuerySet` clone `QueryState` and apply the change — pure functional transformation, no mutation.

## Field Lookups

All Django lookups implemented as a `Lookup` enum dispatched to sea-query `Expr`:

| Lookup            | SQL                         |
|-------------------|-----------------------------|
| `exact` (default) | `= value`                   |
| `iexact`          | `ILIKE value` / `LOWER`     |
| `contains`        | `LIKE %value%`              |
| `icontains`       | `ILIKE %value%`             |
| `startswith`      | `LIKE value%`               |
| `istartswith`     | `ILIKE value%`              |
| `endswith`        | `LIKE %value`               |
| `iendswith`       | `ILIKE %value`              |
| `in`              | `IN (...)`                  |
| `gt`              | `> value`                   |
| `gte`             | `>= value`                  |
| `lt`              | `< value`                   |
| `lte`             | `<= value`                  |
| `range`           | `BETWEEN a AND b`           |
| `date`            | `DATE(col) = value`         |
| `year`            | `YEAR(col) = n`             |
| `month`           | `MONTH(col) = n`            |
| `day`             | `DAY(col) = n`              |
| `isnull`          | `IS NULL` / `IS NOT NULL`   |
| `regex`           | `REGEXP value`              |
| `iregex`          | `REGEXP value` (case-insensitive) |

Lookup parsing: `"field__related__lookup"` is split on `__`, the last segment is tested against known lookups, earlier segments are join traversals.

## Q Objects

```python
from ormpi import Q

# Usage
qs = MyModel.objects.filter(Q(name="foo") | Q(name="bar"))
qs = MyModel.objects.filter(Q(age__gte=18) & ~Q(status="inactive"))
```

`Q` in Rust:
```rust
pub struct Q {
    pub connector: Connector,   // AND | OR
    pub negated: bool,
    pub children: Vec<QNode>,
}
pub enum QNode {
    Leaf(String, PyObject),   // field__lookup, value
    Branch(Q),
}
```

`Q` objects are combined via `__and__`, `__or__`, `__invert__` (Python operators).

## select_related

For `ForeignKey` and `OneToOneField`, `select_related` issues a single SQL JOIN query:

```python
articles = await Article.objects.select_related("author", "category").all()
# Generates: SELECT article.*, author.*, category.* FROM article
#            LEFT JOIN author ON ... LEFT JOIN category ON ...
```

Depth parameter controls how many levels deep to follow: `select_related(depth=2)`.

## prefetch_related

For `ManyToManyField` and reverse FK relations, `prefetch_related` issues separate queries and merges in Python:

```python
authors = await Author.objects.prefetch_related("books").all()
# Query 1: SELECT * FROM author
# Query 2: SELECT * FROM book WHERE author_id IN (...)
# Merge: author._prefetch_cache["books"] = [book, ...]
```

## SQL Generation Flow

```
QuerySet.evaluate()
  → QueryState → SelectStatement (sea-query)
      → filters → Condition tree → ConditionHolder
      → joins (for select_related) → JoinExpr list
      → ORDER BY → OrderExpr list
      → LIMIT / OFFSET
  → QueryBackend.build(stmt) → (sql_string, Values)
  → OrmpiPool.fetch_all(sql, values, db_alias) → Vec<Row>
  → Row → ModelInstance (field by field deserialization)
```

## QuerySet Iteration

```python
# Async iteration
async for article in Article.objects.filter(published=True):
    print(article.title)

# Await full list
articles = await Article.objects.filter(published=True)

# Slicing (returns new QuerySet with LIMIT/OFFSET)
first_ten = Article.objects.all()[:10]
articles = await first_ten
```

`__getitem__` with a slice sets LIMIT and OFFSET on the QueryState and returns a new QuerySet.
`__getitem__` with an integer returns a coroutine that fetches the single row.
