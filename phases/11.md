# Phase 11 — Cleanup, Correctness & Auto-Sync

## Motivation

After reviewing the full design, four issues were identified that need to be resolved before the first stable release:

1. **Django-specific cruft** — `help_text`, `blank`, and `app_label`/`app_name` are Django application-framework concepts with no value in a standalone ORM. They pollute the API and the internal structs without providing anything useful.

2. **Unnecessary AutoField hierarchy** — Django's `AutoField` / `BigAutoField` / `SmallAutoField` exist because Django predates the common convention of just adding `primary_key=True, auto_increment=True` to a plain integer field. In ormpi, the cleaner approach is a single implicit auto-increment BigInteger primary key (injected if none is declared), with the option for a user to declare their own via `BigIntegerField(primary_key=True, auto_increment=True)`.

3. **Missing descriptor ↔ instance-value wiring** — The field descriptor's `__get__` must read from `instance._ormpi_values[self.attname]` and `__set__` must write to both `_ormpi_values` and `_ormpi_dirty`. This round-trip was described in earlier phases but never given an explicit, standalone implementation task. Without it, `instance.title` after a `get()` call returns nothing useful.

4. **Auto-sync (syncdb) mode** — Not every project uses migrations. For small projects and scripts, the user just wants `await ormpi.configure(...)` to ensure every registered model's table exists in the database. This is analogous to Django's old `syncdb`, SQLAlchemy's `Base.metadata.create_all()`, or Tortoise ORM's `generate_schemas()`.

## Goals

- Remove `help_text`, `blank`, `app_label`, `app_name` everywhere (structs, PyO3 classes, stubs, tests).
- Replace the three AutoField PyO3 classes with a single `auto_increment` boolean kwarg on `IntegerField` and `BigIntegerField`. The implicit PK injected by the model registry becomes `BigIntegerField(primary_key=True, auto_increment=True)`.
- Ensure the descriptor `__get__`/`__set__` correctly reads and writes `_ormpi_values` on the model instance, and that `rows_to_model_instances()` fills `_ormpi_values` from the database row.
- Add `auto_sync: bool = False` option to `configure()`. When `true`, ormpi calls `CREATE TABLE IF NOT EXISTS` for every registered model immediately after all pools are ready, without touching any migration file or CLI.

## Acceptance Criteria

- [ ] `FieldDef` struct has no `help_text` or `blank` field
- [ ] `ModelDef` / `ModelMeta` struct has no `app_label` or `app_name` field
- [ ] No `AutoField`, `BigAutoField`, `SmallAutoField` in Python API or stubs
- [ ] `BigIntegerField(primary_key=True, auto_increment=True)` produces correct DDL on all three backends
- [ ] Implicit PK is a `BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY` (MySQL), `BIGSERIAL PRIMARY KEY` (Postgres), `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite)
- [ ] After `Author.objects.get(pk=1)`, `author.name` returns the correct value from the DB row
- [ ] After `author.name = "new"`, `author._ormpi_dirty == {"name"}` before `save()`
- [ ] `await ormpi.configure({"default": {...}}, auto_sync=True)` creates all model tables
- [ ] `auto_sync=False` (default) leaves tables untouched — no DDL emitted
- [ ] All existing tests still pass after cleanup
