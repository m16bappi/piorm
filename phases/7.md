# Phase 7: Migration Engine

## Goal
Implement a full, Django-equivalent migration system: automatic diff-based migration generation, versioned migration files with `up`/`down` operations, a dependency graph, and a migration executor that records applied migrations. All migration logic lives in Rust; Python interacts only through the CLI.

## Scope
- `MigrationRecorder` — creates and manages the `ormpi_migrations` tracking table
- `ProjectState` — snapshot of the full schema at any migration version
- `MigrationAutoDetector` — diffs two `ProjectState`s to produce migration operations
- Migration operations: `CreateModel`, `DeleteModel`, `AddField`, `RemoveField`, `AlterField`, `RenameField`, `AddIndex`, `RemoveIndex`, `AddConstraint`, `RemoveConstraint`, `RunSQL`, `RunPython`
- Migration file serialization — TOML-based migration files with `up` and `down` sections
- `MigrationGraph` — dependency-aware topological ordering
- `MigrationExecutor` — applies/reverses migrations in dependency order
- Squash migrations support
- `--fake` flag support

## Migration File Format

Migration files live in `migrations/` directory at the Python package root. Each file is a TOML file:

```toml
# migrations/0001_initial.toml
[migration]
name = "0001_initial"
dependencies = []

[[operations]]
type = "CreateModel"
name = "User"
fields = [
  { name = "id",         type = "BigAutoField", primary_key = true },
  { name = "username",   type = "CharField",    max_length = 150, unique = true },
  { name = "email",      type = "EmailField",   max_length = 254 },
  { name = "created_at", type = "DateTimeField", auto_now_add = true },
]
[operations.meta]
db_table = "users"
ordering = ["-created_at"]

# ---

# migrations/0002_add_bio.toml
[migration]
name = "0002_add_bio"
dependencies = ["0001_initial"]

[[operations]]
type = "AddField"
model = "User"
name = "bio"
field = { type = "TextField", null = true, blank = true }

[[operations.down]]   # explicit reverse
type = "RemoveField"
model = "User"
name = "bio"
```

## Migration Operations

Each operation implements a `MigrationOperation` trait:

```rust
pub trait MigrationOperation: Send + Sync {
    fn name(&self) -> &str;
    /// Mutate the ProjectState forward
    fn state_forwards(&self, state: &mut ProjectState);
    /// Mutate the ProjectState backward
    fn state_backwards(&self, state: &mut ProjectState);
    /// Generate SQL for the UP direction
    fn database_forwards(&self, backend: &QueryBackend) -> Vec<String>;
    /// Generate SQL for the DOWN direction
    fn database_backwards(&self, backend: &QueryBackend) -> Vec<String>;
}
```

Full operation list:

| Operation          | UP SQL                        | DOWN SQL                          |
|--------------------|-------------------------------|-----------------------------------|
| `CreateModel`      | `CREATE TABLE`                | `DROP TABLE`                      |
| `DeleteModel`      | `DROP TABLE`                  | `CREATE TABLE` (stored state)     |
| `AddField`         | `ALTER TABLE ADD COLUMN`      | `ALTER TABLE DROP COLUMN`         |
| `RemoveField`      | `ALTER TABLE DROP COLUMN`     | `ALTER TABLE ADD COLUMN`          |
| `AlterField`       | `ALTER TABLE MODIFY/ALTER`    | Reverse alter                     |
| `RenameField`      | `ALTER TABLE RENAME COLUMN`   | Reverse rename                    |
| `RenameModel`      | `ALTER TABLE RENAME TO`       | Reverse rename                    |
| `AddIndex`         | `CREATE INDEX`                | `DROP INDEX`                      |
| `RemoveIndex`      | `DROP INDEX`                  | `CREATE INDEX`                    |
| `AddConstraint`    | `ALTER TABLE ADD CONSTRAINT`  | `ALTER TABLE DROP CONSTRAINT`     |
| `RemoveConstraint` | `ALTER TABLE DROP CONSTRAINT` | Re-add constraint                 |
| `RunSQL`           | Arbitrary SQL                 | Provided `reverse_sql` or NOOP    |
| `RunPython`        | Call Python function          | Call `reverse_func` or NOOP       |
| `CreateM2MTable`   | `CREATE TABLE` junction       | `DROP TABLE` junction             |

## MigrationAutoDetector

Compares `from_state: ProjectState` (current migrations) with `to_state: ProjectState` (current model definitions):

```rust
pub struct AutoDetector {
    from_state: ProjectState,
    to_state: ProjectState,
}

impl AutoDetector {
    pub fn detect_changes(&self) -> Vec<Box<dyn MigrationOperation>> {
        let mut ops = vec![];
        // 1. New models → CreateModel
        // 2. Deleted models → DeleteModel
        // 3. New fields → AddField
        // 4. Removed fields → RemoveField
        // 5. Changed field definitions → AlterField
        // 6. Renamed fields (heuristic: same type, one removed one added) → RenameField
        // 7. Changed Meta (ordering, unique_together, indexes) → AlterModelOptions
        ops
    }

    fn build_migration_name(&self, ops: &[Box<dyn MigrationOperation>]) -> String {
        // Auto-generate: 000N_auto_YYYYMMDD_HHMM
        // Or: 000N_<model_name>_<operation_hint>
    }
}
```

## MigrationGraph

pub struct MigrationGraph {

## MigrationExecutor

```rust
pub struct MigrationExecutor {
    recorder: MigrationRecorder,
    graph: MigrationGraph,
    backend: QueryBackend,
}

impl MigrationExecutor {
    pub async fn migrate(&self, target: Option<&str>, fake: bool) -> Result<()>;
    pub async fn rollback_to(&self, target: &str, fake: bool) -> Result<()>;
}
```

Each migration runs in a transaction: if any operation fails, the entire migration rolls back and is not recorded as applied.

## SQLite ALTER TABLE Workaround

SQLite does not support `ALTER TABLE DROP COLUMN` or `ALTER TABLE MODIFY COLUMN` natively (before v3.35). For SQLite:
1. Create new table with desired schema.
2. Copy data: `INSERT INTO new_table SELECT ... FROM old_table`.
3. Drop old table.
4. Rename new to old.
All within a transaction.

## Deliverables
1. `makemigrations` auto-detects all model changes and generates correct TOML files.
2. `migrate` applies all pending migrations in dependency order.
3. `migrate appname 0001` migrates to specific version.
4. `migrate appname zero` rolls back all migrations for an app.
5. Migrations run in transactions — failure leaves DB unchanged.
6. `--fake` marks as applied without executing SQL.
