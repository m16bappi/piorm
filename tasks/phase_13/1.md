# Task 13.1 — Generic Null-Aware Field Descriptors (`fields.pyi`)

## Objective

Rewrite `python/ormpi/fields.pyi` so that every field class is generic on its Python-level
value type `T`. The `null` parameter at construction time narrows `T` at the call site:
`CharField(null=True)` produces `CharField[str | None]`, while the default `CharField(...)`
produces `CharField[str]`. The `__get__` descriptor returns `T` on instance access (not `Any`),
enabling precise IDE type inference for model attributes.

---

## Background: Why `__new__` overloads?

`__init__` cannot change the type that is returned by a constructor call — the return type of
`Foo(...)` is always `Foo`. To make `CharField(null=True)` produce a different *generic
instantiation* (`CharField[str | None]`) than `CharField(null=False)` (`CharField[str]`),
we override `__new__`, which **can** specify a return type in stubs. Type checkers (pyright
fully, mypy with `--python-version 3.12`) resolve `__new__` overloads at the call site.

In a `.pyi` stub there is no implementation body — only overload signatures are needed.
The final non-overloaded `__init__` carries the real parameter names and defaults so
editors show parameter hints.

## Key Design Decisions

### Why `T: int | (int | None) = int` instead of just `T = int`?

PEP 695 constraint syntax `T: (A, B)` restricts `T` to be exactly `A` or exactly `B`. Writing
`T: int | (int | None)` means type checkers will not allow arbitrary types like `str` to be
substituted for `T` in `IntegerField[T]`. Without this constraint, `IntegerField[str]` would
be accepted, which is semantically wrong.

The fallback default `= int` means `IntegerField()` (without a type argument) infers `T = int`.

### Third overload on `__new__` (non-literal `null: bool`)

When user code passes a runtime-variable `null_flag: bool` to the field constructor, neither
`Literal[True]` nor `Literal[False]` matches. The third overload catches this case and returns
the non-None type (e.g., `CharField[str]`). This is the conservative default — it errs on the
side of non-nullable rather than forcing the user to deal with `str | None` everywhere when the
actual value might never be `None`.

### `ForeignKey[M, T]` — two type parameters

`ForeignKey` has two independent dimensions: the related model type (`M`) and whether the field
itself is nullable (`T` is `M | None` or `M`). Two separate type parameters capture this cleanly.
The `M` parameter enables future phases to type forward-access (`article.author → Author`).

### `JSONField[T = Any]`

JSON can hold any serializable value. The field defaults to `Any` but users who want narrower
types can annotate explicitly: `data: dict[str, int] = JSONField()`. No `__new__` overload
changes the type based on `null` because `None` is a valid JSON value anyway and `Any` already
includes it.
