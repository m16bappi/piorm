# Task 15.1 — Fix Q Object Type Identity (`ormpi.expr.Q` ≠ `ormpi._core.Q`)

## Failing Tests

```
TestQObjects::test_q_or
TestQObjects::test_q_and
TestQObjects::test_q_not
TestQObjects::test_q_nested
TestQObjects::test_q_combined_with_kwargs
TestQObjects::test_q_double_not
TestGet::test_get_with_q_object
TestQuerySetDelete::test_delete_with_q_or
TestQuerySetDelete::test_delete_with_q_not
TestQuerySetUpdateFiltered::test_update_with_q_or
TestQuerySetUpdateFiltered::test_update_with_q_and
TestQuerySetUpdateFiltered::test_update_with_q_not
```

Error:
```
TypeError: filter() positional arguments must be Q objects
```

## Root Cause

`ormpi.expr.Q` and `ormpi._core.Q` are **different Python type objects** (different `id()`).
Verified with:

```python
import ormpi._core as core, ormpi.expr as expr
assert core.Q is expr.Q   # FAILS — two distinct type objects
```

`QuerySet.filter()` in Rust does `arg.downcast::<PyQ>()` which checks Python type identity
against the `PyQ` class registered in `ormpi._core`. When `Q` is imported via `ormpi.expr`
(the public-facing module), it is a different Python class object, so the type check fails
even though both look like "Q" to the user.

The divergence is caused by how PyO3 + Python's import machinery interact when the
`ormpi.expr` module is first imported during `ormpi.__init__` initialisation before
`ormpi._core` is fully settled in `sys.modules`. The fallback class in the `except
ImportError` block creates a second, pure-Python `Q` class that survives in some code
paths.

## Fix — `python/ormpi/expr.py`

Remove the `try/except ImportError` fallback and import unconditionally. The `.so` is
always present in a built package; the fallback was only ever needed for type-stub-only
CI runs, which should use a separate stub file instead.

```python
# BEFORE (expr.py)
try:
    from ormpi._core import Q, Aggregate, Count, Sum, Avg, Max, Min  # type: ignore[attr-defined]
except ImportError:
    # Pure-Python fallback used during stub-only / CI type-check runs
    class Q:  # type: ignore[no-redef]
        ...
    class Count(Aggregate): ...
    # etc.

# AFTER (expr.py)
from ormpi._core import Q, Aggregate, Count, Sum, Avg, Max, Min  # type: ignore[attr-defined]
```

Additionally, ensure `ormpi/__init__.py` imports `ormpi._core` **before** `ormpi.expr` so
that the Rust extension is initialised first:

```python
# ormpi/__init__.py — make sure _core is imported first
from ormpi._core import close, execute_raw, get_version   # already present, keep first
import ormpi.expr as expr                                  # must come after _core is loaded
```

## Fix — `ormpi-py/src/query/queryset.rs` (defensive fallback)

As a belt-and-suspenders fix, change `filter()` to use `extract::<PyRef<PyQ>>()` instead
of `downcast::<PyQ>()`. `extract` goes through the Python `__class__` check and is more
forgiving of class identity differences:

```rust
// BEFORE
let q = arg.downcast::<PyQ>().map_err(|_| {
    pyo3::exceptions::PyTypeError::new_err(
        "filter() positional arguments must be Q objects",
    )
})?;
state.filters.filters.push(FilterNode::Q(q.borrow().node.clone()));

// AFTER
let q = arg.extract::<PyRef<crate::query::q::PyQ>>().map_err(|_| {
    pyo3::exceptions::PyTypeError::new_err(
        "filter() positional arguments must be Q objects",
    )
})?;
state.filters.filters.push(FilterNode::Q(q.node.clone()));
```

Apply the same change in `exclude()` if it has the same downcast pattern.

## Files Changed

| File | Change |
|------|--------|
| `python/ormpi/expr.py` | Remove `try/except ImportError` block; unconditional import |
| `ormpi-py/src/query/queryset.rs` | `filter()` / `exclude()`: `downcast` → `extract::<PyRef<PyQ>>()` |
