## Bug 1 — `bulk_create` Returns `int` Instead of `list[Model]`

### Error

```python
result = await Author.objects.bulk_create([Author(name="A", email="a@test.com")])
assert isinstance(result, list)   # FAIL: result is 1 (integer)
```

### Root Cause

`bulk_create` in `queryset.rs` calls `bulk_create_rows()` in `evaluate.rs` which returns
a `count: i64`. The result is returned as a raw integer to Python:

```rust
Python::with_gil(|py| Ok::<PyObject, PyErr>(count.into_py(py)))
```

But the tests expect a `list` of model instances (the inserted objects with their new PKs
populated).

### Fix — `queryset.rs` and `ormpi-core/src/query/evaluate.rs`

Change `bulk_create_rows` to return the last-inserted row IDs, then re-fetch or reconstruct
instances.

**Option A (simpler):** After bulk insert, re-fetch all inserted rows using the returned
row count and the known field values:

```rust
// After bulk_create_rows call, reconstruct instances from input data + assigned PKs
// For SQLite: use last_insert_rowid() - count + 1 .. last_insert_rowid()
// For Postgres/MySQL: collect RETURNING id (need backend-specific handling)
```

**Option B (simplest for correctness):** Change `bulk_create_rows` signature to return
`Vec<i64>` (the new PKs), then for each pk build an instance by combining the input
field values with the assigned `id`:

```rust
// ormpi-core/src/query/evaluate.rs
pub async fn bulk_create_rows(...) -> Result<Vec<i64>> {
    // ... insert rows, collect last_insert_rowid for each chunk
    // For SQLite, after each batch insert, last_insert_rowid is the LAST row's id
    // IDs are sequential: [last_id - batch_len + 1 .. last_id]
}
```

Back in `queryset.rs`:

```rust
let pks = bulk_create_rows(rows_clone, chunk, &pool, &backend, &model_def)
    .await
    .map_err(|e| Python::with_gil(|_py| crate::ormpi_err(e)))?;

Python::with_gil(|py| {
    // Build instances: copy each row's field values + assign pk
    let instances: Vec<PyObject> = pks.iter().zip(rows.iter()).map(|(pk, row_vals)| {
        // create a new model instance with row_vals + id = pk
        let cls = model_class.as_ref().unwrap();
        let instance = cls.bind(py).call0().unwrap();
        let values = instance.getattr("_values").unwrap();
        let d = values.downcast::<PyDict>().unwrap();
        for (k, v) in row_vals {
            d.set_item(k, ormpi_value_to_py(py, v)).unwrap();
        }
        d.set_item("id", pk).unwrap();
        // Clear dirty bits
        instance.setattr("_dirty", 0u64).unwrap();
        instance.setattr("_adding", false).unwrap();
        instance.into()
    }).collect();
    Ok::<PyObject, PyErr>(pyo3::types::PyList::new_bound(py, instances).into())
})
```

### Empty list case

When `objs` is empty, return an empty list immediately (no DB call):

```rust
if rows.is_empty() {
    return pyo3_async_runtimes::tokio::future_into_py(py, async move {
        Python::with_gil(|py| {
            Ok::<PyObject, PyErr>(pyo3::types::PyList::empty_bound(py).into())
        })
    }).map(|b| b.into());
}
```

### `ignore_conflicts` parameter

`bulk_create` has `batch_size` but not `ignore_conflicts`. Add it:

```rust
#[pyo3(signature = (objs, batch_size = None, ignore_conflicts = false))]
fn bulk_create(
    slf: Bound<'_, Self>,
    objs: Vec<PyObject>,
    batch_size: Option<usize>,
    ignore_conflicts: bool,
) -> PyResult<PyObject> { ... }
```

Pass `ignore_conflicts` to `bulk_create_rows` which adds `INSERT OR IGNORE` (SQLite) or
`INSERT ... ON CONFLICT DO NOTHING` (Postgres/MySQL) to the statement.

## Bug 2 — `execute_raw` Fails for DDL Statements (CREATE TABLE)

### Error

```
RuntimeError: Database error: no rows returned by a query that expected to return at least one row
```

### Root Cause

`execute_raw` in `lib.rs` calls an executor that expects a result row to be returned.
DDL statements like `CREATE TABLE IF NOT EXISTS ...` return no rows, causing the error.

### Fix — `ormpi-py/src/lib.rs`, `execute_raw` function

Change the implementation to handle zero-row responses gracefully:

```rust
#[pyfunction]
fn execute_raw(py: Python<'_>, sql: String) -> PyResult<PyObject> {
    pyo3_async_runtimes::tokio::future_into_py(py, async move {
        let pool = { ... get default pool ... };
        // Use execute() not fetch_one() for DDL/DML
        match &pool {
            OrmpiPool::Sqlite(p) => {
                sqlx::query(&sql).execute(p).await
                    .map_err(|e| Python::with_gil(|_py| crate::ormpi_err(OrmpiError::from(e))))?;
            }
            // ... postgres, mysql
        }
        Python::with_gil(|py| Ok::<PyObject, PyErr>(py.None()))
    })
    .map(|b| b.into())
}
```

Return `None` for DDL/DML statements. If the call was expecting a row (e.g. raw SELECT),
use a different function `execute_sql` that returns rows.

## Bug 3 — `SET_NULL` Delete Behaviour

### Error (test_set_null_nullifies_fk_on_parent_delete)

After the `execute_raw` fix (Bug 2), the table creation should succeed. The test then
calls `author.delete()` and expects that `NullableChild.author_id` is set to NULL.

### Current State

`SET_NULL` on delete requires the ORM to:
1. Detect FK fields with `on_delete=SET_NULL` that reference the deleted model
2. Before deleting the parent, issue: `UPDATE nullable_children SET author_id = NULL WHERE author_id = <deleted_pk>`

Verify that the cascade handler in `ormpi-core` implements `SET_NULL`. If not, add it:

```rust
OnDelete::SetNull => {
    let update_sql = format!(
        "UPDATE {} SET {} = NULL WHERE {} = ?",
        child_table, fk_column, fk_column
    );
    // execute update before parent delete
}
```
