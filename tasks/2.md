# Task 2 — Introduce `Connectable` Trait (Pool + Transaction Abstraction)

## Background

The doc's primary Rust recommendation is a `ConnectionTrait` / `ExecutorRef`
abstraction, modelled after SeaORM:

> **`ConnectionTrait` / `ExecutorRef` abstraction** (SeaORM model)
> - `OrmpiPool` and `OrmpiTransaction` both implement a common `Connectable` trait
> - All operation functions (`save_instance`, `delete_instance`, etc.) accept
>   `&dyn Connectable` — no signature change needed when adding transactions

Currently all query execution functions in `ormpi-core/src/executor.rs` accept
`&OrmpiPool` directly. There is no way to run a query against an open
transaction without constructing a raw SQL string and calling `execute_raw`.

This task introduces the `Connectable` trait so that every operation in the
ORM core becomes **location-agnostic** — the caller decides whether it runs
against a pool connection or inside an existing transaction.

## Design

```rust
// ormpi-core/src/connectable.rs

/// Unified abstraction over OrmpiPool and OrmpiTransaction.
///
/// Implementors provide a single entry-point for executing a raw SQL
/// statement and fetching rows.  The ORM core routes all operations through
/// this trait so callers can transparently swap a pool for a transaction.
pub trait Connectable: Send + Sync {
    /// Execute a statement (DDL / DML).  Returns rows-affected.
    fn execute<'s>(
        &'s mut self,
        sql: &'s str,
        params: &'s [crate::value::OrmpiValue],
    ) -> BoxFuture<'s, crate::Result<u64>>;

    /// Fetch all matching rows.
    fn fetch_all<'s>(
        &'s mut self,
        sql: &'s str,
        params: &'s [crate::value::OrmpiValue],
    ) -> BoxFuture<'s, crate::Result<Vec<crate::row::OrmpiRow>>>;
}

impl Connectable for OrmpiPool { … }
impl Connectable for OrmpiTransaction { … }
```

Key design constraints:

- Use `BoxFuture` (from `futures`) to avoid associated-type lifetime complexity
  in the trait object.
- `OrmpiPool::execute` acquires a connection from the pool, runs the query,
  and releases it immediately (connection-per-query, not connection-per-session).
- `OrmpiTransaction::execute` reuses the transaction's borrowed connection.
- The trait is object-safe (`&mut dyn Connectable` is the call-site type at
  the Rust level; `PyTransaction` wraps it behind `Arc<Mutex<…>>`).

## Test Cases

### Unit tests — `ormpi-core/src/connectable.rs` (`#[cfg(test)]`)

**TC-2.1 — `OrmpiPool` satisfies `Connectable`**
```rust
#[tokio::test]
async fn pool_connectable_execute() {
    let pool = make_test_pool().await;
    pool.execute(
        "CREATE TABLE IF NOT EXISTS c_test(id INTEGER)",
        &[],
    ).await.unwrap();
    let rows = pool.fetch_all("SELECT * FROM c_test", &[]).await.unwrap();
    assert!(rows.is_empty());
}
```

**TC-2.2 — `OrmpiTransaction` satisfies `Connectable`**
```rust
#[tokio::test]
async fn transaction_connectable_execute() {
    let pool = make_test_pool().await;
    pool.execute("CREATE TABLE IF NOT EXISTS c_test2(v TEXT)", &[])
        .await.unwrap();
    let mut txn = OrmpiTransaction::begin(&pool, "default").await.unwrap();
    txn.execute(
        "INSERT INTO c_test2 VALUES ('hello')",
        &[],
    ).await.unwrap();
    let rows = txn.fetch_all("SELECT v FROM c_test2", &[]).await.unwrap();
    assert_eq!(rows.len(), 1);
    txn.rollback().await.unwrap();
}
```

**TC-2.3 — Same function works with both pool and transaction**
```rust
async fn count_rows(conn: &mut dyn Connectable, table: &str) -> i64 {
    let rows = conn
        .fetch_all(&format!("SELECT COUNT(*) AS n FROM {table}"), &[])
        .await
        .unwrap();
    rows[0].get_i64("n").unwrap()
}

#[tokio::test]
async fn location_agnostic_helper() {
    let pool = make_test_pool().await;
    pool.execute("CREATE TABLE IF NOT EXISTS la(id INT)", &[]).await.unwrap();
    pool.execute("INSERT INTO la VALUES (1)", &[]).await.unwrap();

    // via pool
    assert_eq!(count_rows(&mut pool.clone(), "la").await, 1);

    // via transaction (sees the committed row)
    let mut txn = OrmpiTransaction::begin(&pool, "default").await.unwrap();
    assert_eq!(count_rows(&mut txn, "la").await, 1);
    txn.rollback().await.unwrap();
}
```

**TC-2.4 — Writes through transaction are invisible to pool until commit**
```rust
#[tokio::test]
async fn transaction_write_isolation() {
    let pool = make_test_pool().await;
    pool.execute("CREATE TABLE IF NOT EXISTS iso(id INT)", &[]).await.unwrap();

    let mut txn = OrmpiTransaction::begin(&pool, "default").await.unwrap();
    txn.execute("INSERT INTO iso VALUES (99)", &[]).await.unwrap();

    // Pool sees 0 rows (not yet committed)
    let count_before = count_rows(&mut pool.clone(), "iso").await;
    assert_eq!(count_before, 0);

    txn.commit().await.unwrap();

    // Pool sees 1 row after commit
    let count_after = count_rows(&mut pool.clone(), "iso").await;
    assert_eq!(count_after, 1);
}
```

### Integration test — `__tests__/transactions/test_connectable.py`

**TC-2.5 — `create()` routed through a transaction is invisible until commit**
```python
@pytest.mark.asyncio
async def test_create_via_transaction_invisible_before_commit():
    txn = await ormpi.begin()
    # Future: Author.objects.create(using=txn, ...) — for now, raw execute_raw
    await txn.execute_raw(
        "INSERT INTO authors(name, email, active) VALUES ('Txn', 'txn@test.com', 1)"
    )
    # Another connection (pool) should not see the row yet
    count = await Author.objects.filter(email="txn@test.com").count()
    assert count == 0
    await txn.rollback()
```
