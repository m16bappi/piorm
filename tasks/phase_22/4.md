# Task 22.4 — Consolidate `json_to_py` Duplication

## Problem

`lib.rs` contains a private `json_to_py` function for converting `serde_json::Value`
to `PyObject`:

```rust
// lib.rs
fn json_to_py(py: Python<'_>, val: serde_json::Value) -> PyObject {
    match val {
        serde_json::Value::Null     => py.None(),
        serde_json::Value::Bool(b)  => b.into_py(py),
        serde_json::Value::Number(n) => { ... }
        serde_json::Value::String(s) => s.into_py(py),
        serde_json::Value::Array(a)  => { ... }
        serde_json::Value::Object(o) => { ... }
    }
}
```

`convert.rs` also handles `OrmpiValue::Json(j)` by calling `json.loads(j.to_string())`:

```rust
// convert.rs
OrmpiValue::Json(j) => {
    py.import_bound("json")
        .and_then(|m| m.getattr("loads"))
        .and_then(|loads| loads.call1((j.to_string(),)))
        .map(|o| o.into())
        .unwrap_or_else(|_| j.to_string().into_py(py))
}
```

These two approaches are inconsistent:
- `lib.rs` walks the JSON tree natively (fast, no Python import)
- `convert.rs` serializes to string and re-parses via `json.loads` (slow, two allocations)

Both paths produce the same Python object type, but the performance difference is
significant for large JSON values.

## Fix

### Step 1 — Move `json_to_py` to `convert.rs`

Make it `pub(crate)` so both `lib.rs` and `convert.rs` can use it:

```rust
// convert.rs

/// Recursively convert a `serde_json::Value` to a Python object without going
/// through JSON serialization/deserialization.
pub(crate) fn json_value_into_py(py: Python<'_>, val: serde_json::Value) -> PyObject {
    match val {
        serde_json::Value::Null      => py.None(),
        serde_json::Value::Bool(b)   => b.into_py(py),
        serde_json::Value::Number(n) => {
            if let Some(i) = n.as_i64() { i.into_py(py) }
            else if let Some(f) = n.as_f64() { f.into_py(py) }
            else { n.to_string().into_py(py) }
        }
        serde_json::Value::String(s) => s.into_py(py),
        serde_json::Value::Array(a)  => {
            let items: Vec<PyObject> = a.into_iter()
                .map(|v| json_value_into_py(py, v))
                .collect();
            items.into_py(py)
        }
        serde_json::Value::Object(o) => {
            use pyo3::types::PyDict;
            let dict = PyDict::new_bound(py);
            for (k, v) in o {
                dict.set_item(k, json_value_into_py(py, v))
                    .unwrap_or_default(); // dict.set_item only fails on MemoryError
            }
            dict.into()
        }
    }
}
```

Remove `json_to_py` from `lib.rs` and import `json_value_into_py` from `convert`.

### Step 2 — Update `OrmpiValue::Json` handling in `value_into_py`

Replace the `json.loads(j.to_string())` roundtrip with the native tree walk:

```rust
// convert.rs — value_into_py
OrmpiValue::Json(j) => json_value_into_py(py, j),
```

This eliminates:
- One `py.import_bound("json")` call per JSON value
- One `j.to_string()` serialization
- One Python `json.loads()` parse

### Step 3 — Fix `dict.set_item().unwrap_or_default()`

`PyDict::set_item` returns `PyResult<()>`. Using `.unwrap_or_default()` silently drops
`MemoryError`. While this is unlikely to matter in practice (and `IntoPy` is infallible),
add a comment:

```rust
// SAFETY: set_item only fails on Python MemoryError, which aborts the interpreter
// anyway. The unwrap_or_default matches the infallible contract of json_value_into_py.
dict.set_item(k, json_value_into_py(py, v)).unwrap_or_default();
```

- [ ] `json_to_py` removed from `lib.rs`
