# Task 22.6 — Improve `DateTimeTz` Python Conversion in `convert.rs`

## Problem

`OrmpiValue::DateTimeTz` is serialized as an RFC 3339 string instead of a native
Python `datetime` object:

```rust
// convert.rs — current
OrmpiValue::DateTimeTz(dt) => {
    // Return as ISO 8601 string with timezone info
    dt.to_rfc3339().into_py(py)
}
```

All other temporal values (`Date`, `Time`, `DateTime`) produce native Python
`datetime.date`, `datetime.time`, `datetime.datetime` objects. The inconsistency means:

```python
# Python side
obj.created_at        # → datetime.datetime (naive, for DateTime fields)
obj.updated_at        # → str "2024-01-01T12:00:00+00:00" (for DateTimeTz fields)
```

This breaks any code that tries to compare, format, or arithmetic-operate on
`DateTimeTz` values as datetimes.

## Fix

Convert `DateTimeTz` to a timezone-aware Python `datetime.datetime` with UTC timezone:

```rust
OrmpiValue::DateTimeTz(dt) => {
    // Build datetime.timezone.utc
    let datetime_mod = py.import_bound("datetime")
        .and_then(|m| m.getattr("datetime"))
        .and_then(|cls| {
            // datetime(year, month, day, hour, minute, second, microsecond, tzinfo)
            use chrono::Datelike;
            use chrono::Timelike;
            let tzinfo = py.import_bound("datetime")
                .and_then(|m| m.getattr("timezone"))
                .and_then(|tz| tz.getattr("utc"))?;
            cls.call1((
                dt.year(),
                dt.month(),
                dt.day(),
                dt.hour(),
                dt.minute(),
                dt.second(),
                dt.timestamp_subsec_micros(),
                tzinfo,
            ))
        });

    datetime_mod
        .map(|o| o.into())
        .unwrap_or_else(|_| dt.to_rfc3339().into_py(py)) // fallback to string
}
```

The fallback to RFC 3339 string is kept so that if Python datetime construction fails
for any reason, the value is still usable (and the caller can detect the degraded case
by type-checking).

## Consistency Audit

While fixing `DateTimeTz`, audit the other temporal conversions for the same class of
issue:

| Variant | Current Python type | Expected Python type |
|---|---|---|
| `Date` | `datetime.date` | `datetime.date` ✅ |
| `Time` | `datetime.time` | `datetime.time` ✅ |
| `DateTime` | `datetime.datetime` (naive) | `datetime.datetime` (naive) ✅ |
| `DateTimeTz` | `str` (RFC 3339) | `datetime.datetime` (aware, UTC) ❌ |

Also note: `Time` currently loses microseconds:
```rust
cls.call1((t.hour(), t.minute(), t.second()))  // ← no microseconds
```

Fix to:
```rust
cls.call1((t.hour(), t.minute(), t.second(), t.nanosecond() / 1000))
```

And `DateTime` loses microseconds the same way. Fix both.

## Acceptance Criteria

- [ ] `OrmpiValue::DateTimeTz` → Python `datetime.datetime` with `tzinfo=timezone.utc`
- [ ] `OrmpiValue::Time` includes microseconds
- [ ] `OrmpiValue::DateTime` includes microseconds
- [ ] RFC 3339 string fallback preserved for `DateTimeTz`
- [ ] Python tests that read `DateTimeTz` fields receive `datetime.datetime` objects
- [ ] `isinstance(obj.updated_at, datetime.datetime)` and `obj.updated_at.tzinfo is not None`
