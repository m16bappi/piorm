# Task 22.2 — Fix `unwrap()` Calls in `ormpi-py`

## Problem

Several `unwrap()` calls in production PyO3 code silently panic instead of surfacing
errors as Python exceptions:

### A — `list.append().unwrap()` in `lib.rs`

```rust
// lib.rs — Row::into_py
fn into_py(self, py: Python<'_>) -> PyObject {
    let list = PyList::empty_bound(py);
    for (name, val) in self.0 {
        let val_py = json_to_py(py, val);
        let tup = PyTuple::new_bound(py, [name.into_py(py), val_py]);
        list.append(&tup).unwrap();  // ← panics if Python raises MemoryError
    }
    list.into()
}
```

`PyList::append` returns `PyResult<()>`; `.unwrap()` turns a Python MemoryError or
other exception into a Rust panic that unwinds through PyO3, which is UB in FFI code.

### B — `ModelRegistry::global().read().unwrap()` in `model/instance.rs`

```rust
let reg = ModelRegistry::global();
let guard = reg.read().unwrap();  // ← lock-poisoning panic
```

Lock poisoning here crashes the Python interpreter. Should map to a `PyRuntimeError`.

### C — `unwrap_or_default()` used to mask type-name extraction failure

```rust
let type_name = obj.get_type().name()
    .map(|n| n.extract::<String>().unwrap_or_default())  // masks extraction errors
    .unwrap_or_default();
```

`unwrap_or_default()` is safer than `unwrap()`, but silently treats type-name
extraction failures as an empty string, which falls through to a less specific branch.
Add a comment explaining this is intentional and the fallback is safe.

## Fix

### Fix A — `Row::into_py` propagation

`IntoPy::into_py` cannot return `Result`, so the error must be mapped before entering
the infallible conversion. Refactor `Row` to use a failable helper:

```rust
impl Row {
    fn try_into_pylist(self, py: Python<'_>) -> PyResult<PyObject> {
        let list = PyList::empty_bound(py);
        for (name, val) in self.0 {
            let val_py = json_to_py(py, val);
            let tup = PyTuple::new_bound(py, [name.into_py(py), val_py]);
            list.append(&tup)?;  // propagate as PyErr
        }
        Ok(list.into())
    }
}
```

Update callers to use `row.try_into_pylist(py)?` rather than `row.into_py(py)`.

### Fix B — Registry read in `model/instance.rs`

```rust
let reg = ModelRegistry::global();
let guard = reg.read().map_err(|_| {
    pyo3::exceptions::PyRuntimeError::new_err(
        "Model registry lock poisoned"
    )
})?;
```

### Fix C — Document the safe fallback

```rust
// `get_type().name()` returns `PyResult<&str>`; `extract::<String>()` returns
// `PyResult<String>`. Both fallbacks give "" which causes `py_to_value` to skip
// the _FExpr branch and try byte extraction. This is intentional — unknown types
// fall through to the final PyValueError at the bottom of the function.
let type_name = obj.get_type().name()
    .map(|n| n.extract::<String>().unwrap_or_default())
    .unwrap_or_default();
```

## Acceptance Criteria

- [ ] Zero `.unwrap()` calls in non-test `ormpi-py` source
- [ ] `Row` uses failable `try_into_pylist` helper; callers propagate `PyResult`
- [ ] Registry reads map `PoisonError` to `PyRuntimeError`
- [ ] `unwrap_or_default()` fallbacks are documented with comments
- [ ] `cargo clippy -p ormpi-py -- -D clippy::unwrap_used` passes (or suppressions
      documented with `#[expect(...)]`)
