# Task 22.1 — Rename / Restructure Value Conversion Functions in `convert.rs`

## Problem

`ormpi-py` has two conversion functions with names that are opaque and placed
inconsistently:

| Current name | Location | Direction |
|---|---|---|
| `value_to_py(py, &OrmpiValue) -> PyObject` | `convert.rs` | Rust → Python |
| `py_to_ormpi_value(&Bound<PyAny>) -> PyResult<OrmpiValue>` | `model/instance.rs` | Python → Rust |

Issues:
1. **Both directions should live in the same module** (`convert.rs`) so the conversion
   layer is a single place to read and modify.
2. `value_to_py` is a verbose, non-idiomatic name. The PyO3 convention for Rust → Python
   conversions is `into_py` / `IntoPy` trait. We cannot implement `IntoPy<PyObject>` for
   `OrmpiValue` directly (orphan rule), but we can introduce a local newtype.
3. `py_to_ormpi_value` in `model/instance.rs` is far from `value_to_py` — finding either
   function requires knowing two different file locations.

## Fix

### Step 1 — Move `py_to_ormpi_value` into `convert.rs`

```rust
// ormpi-py/src/convert.rs

/// Convert a Python object to `OrmpiValue`.
///
/// Type detection order:
///   None → Null
///   bool (before int, Python bool subclasses int) → Bool
///   int → Int
///   float → Float
///   str → Text
///   list/tuple → List (recursive)
///   bytes → Bytes
///   _FExpr → FExpr (expression tree)
///   model instance (has `.pk`) → Int (primary key)
///   fallback: PyValueError
pub(crate) fn py_to_value(obj: &Bound<'_, PyAny>) -> PyResult<OrmpiValue> {
    // ... (moved from model/instance.rs unchanged, just renamed)
}
```

Remove the function from `model/instance.rs` and update all callers to import from
`crate::convert`.

### Step 2 — Rename `value_to_py` → `value_into_py`

The `into_` prefix signals ownership/consumption semantics and aligns with Rust naming
conventions (`into_py` is the method name used by PyO3's `IntoPy` trait):

```rust
pub(crate) fn value_into_py(py: Python<'_>, value: &OrmpiValue) -> PyObject {
    // ... body unchanged
}
```

Update all callers (grep for `value_to_py`).

### Step 3 — (Optional) Introduce a `PyValue` newtype for ergonomic conversion

If there are many call sites using `value_into_py(py, v)`, a thin newtype reduces
boilerplate:

```rust
/// Newtype wrapper enabling `PyValue(v).into_py(py)` syntax at call sites.
pub(crate) struct PyValue<'a>(pub &'a OrmpiValue);

impl IntoPy<PyObject> for PyValue<'_> {
    fn into_py(self, py: Python<'_>) -> PyObject {
        value_into_py(py, self.0)
    }
}
```

Call sites become `PyValue(v).into_py(py)` instead of `value_into_py(py, v)`. Apply
this only if it meaningfully reduces repetition (≥ 5 call sites benefit).
