# Task 7: Fix Silent `unwrap_or_default()` on PK After Postgres INSERT

## Problem

`piorm-core/src/model/executor.rs` `insert_instance` silently swallows a type mismatch or missing PK column after a Postgres INSERT … RETURNING:

```rust
// model/executor.rs lines 127–133
PiormPool::Postgres(p) => {
    // ...
    let row = sqlx::query_with(&sql, args).fetch_one(p).await?;
    let id: i64 = row
        .try_get(model_def.pk_field.as_str())
        .unwrap_or_default();   // ← silently returns 0 on any error
    Ok(PiormValue::Int(id))
}
```

`try_get` fails when:
- The column name in `RETURNING` doesn't match `pk_field` (e.g. aliased column)
- The PK type is not `i64` (e.g. UUID primary key)
- The row is unexpectedly null

In all these cases `unwrap_or_default()` returns `0`, which is then stored as the instance's PK. The Python layer will silently treat a newly-saved object as having `pk=0`, causing every subsequent UPDATE to fail or corrupt data.

## Fix

Replace `unwrap_or_default()` with a proper `map_err` that converts the sqlx decode error into an `PiormError::FieldError`:

```rust
// In insert_instance, Postgres arm — replace lines 127–133 with:
PiormPool::Postgres(p) => {
    let mut stmt = Query::insert();
    stmt.into_table(Alias::new(&model_def.table_name))
        .columns(columns)
        .values_panic(row_values)
        .returning_col(pk_col);
    let (sql, sea_vals) = backend.build_insert(&stmt);
    let args = postgres_arguments(sea_vals);
    let row = sqlx::query_with(&sql, args).fetch_one(p).await?;
    let id: i64 = row
        .try_get(model_def.pk_field.as_str())
        .map_err(|e| PiormError::FieldError {
            model: model_def.model_name.clone(),
            field: model_def.pk_field.clone(),
            message: format!(
                "failed to read generated primary key from RETURNING clause: {e}"
            ),
        })?;
    Ok(PiormValue::Int(id))
}
```

## Secondary Issue: Same Pattern in `fetch_instance`

`fetch_instance` (line 130 area, after Task 2 refactor) also uses `.unwrap_or_default()` when extracting the `i64` pk from a fetched row. Apply the same `map_err` + `?` treatment there.
