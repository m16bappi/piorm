# Task 21.3 — Reduce `QueryBackend` Boilerplate with a Macro

## Problem

`QueryBackend` in `backend.rs` has 8 methods, each with an identical 3-arm `match`
that only differs in the builder type passed:

```rust
pub fn build_select(&self, stmt: &SelectStatement) -> (String, Values) {
    match self.0 {
        DatabaseBackend::Sqlite   => stmt.build(SqliteQueryBuilder),
        DatabaseBackend::Mysql    => stmt.build(MysqlQueryBuilder),
        DatabaseBackend::Postgres => stmt.build(PostgresQueryBuilder),
    }
}

pub fn build_insert(&self, stmt: &InsertStatement) -> (String, Values) {
    match self.0 {
        DatabaseBackend::Sqlite   => stmt.build(SqliteQueryBuilder),
        DatabaseBackend::Mysql    => stmt.build(MysqlQueryBuilder),
        DatabaseBackend::Postgres => stmt.build(PostgresQueryBuilder),
    }
}
// ... 6 more identical patterns
```

This is ~70 lines of pure structural repetition. Every time a new statement type is
added (or a backend), all 8 methods must be updated.

## Fix

### Option A — `with_builder` dispatcher method (preferred)

Extract the backend-selection logic into one place and delegate:

```rust
impl QueryBackend {
    /// Calls `f` with the concrete sea-query builder for this backend.
    fn with_builder<F, R>(&self, f: F) -> R
    where
        F: FnOnce(&dyn sea_query::QueryBuilder) -> R,
    {
        match self.0 {
            DatabaseBackend::Sqlite   => f(&SqliteQueryBuilder),
            DatabaseBackend::Mysql    => f(&MysqlQueryBuilder),
            DatabaseBackend::Postgres => f(&PostgresQueryBuilder),
        }
    }
}
```

Then each public method becomes a one-liner:

```rust
pub fn build_select(&self, stmt: &SelectStatement) -> (String, Values) {
    self.with_builder(|b| stmt.build_ref(b))
}

pub fn build_insert(&self, stmt: &InsertStatement) -> (String, Values) {
    self.with_builder(|b| stmt.build_ref(b))
}
```

> Note: check whether sea-query exposes a `QueryBuilder` object-safe trait and a
> `build_ref(&dyn QueryBuilder)` method. If not, use Option B.

### Option B — Declarative macro (fallback)

If `QueryBuilder` is not object-safe, a declarative macro eliminates the repetition
without dynamic dispatch overhead:

```rust
macro_rules! dispatch_build {
    ($self:expr, $stmt:expr, $method:ident) => {
        match $self.0 {
            DatabaseBackend::Sqlite   => $stmt.$method(SqliteQueryBuilder),
            DatabaseBackend::Mysql    => $stmt.$method(MysqlQueryBuilder),
            DatabaseBackend::Postgres => $stmt.$method(PostgresQueryBuilder),
        }
    };
}

impl QueryBackend {
    pub fn build_select(&self, stmt: &SelectStatement) -> (String, Values) {
        dispatch_build!(self, stmt, build)
    }

    pub fn build_insert(&self, stmt: &InsertStatement) -> (String, Values) {
        dispatch_build!(self, stmt, build)
    }

    pub fn build_table_create(&self, stmt: &TableCreateStatement) -> String {
        dispatch_build!(self, stmt, to_string)
    }
    // ...
}
```

Keep the macro `pub(crate)` or file-local only — it is an implementation detail, not
part of the public API.

### Step — Verify sea-query API

Before choosing Option A or B, check `sea-query/src/` for:
- Whether `QueryBuilder` is a trait with `build()` and `to_string()` methods
- Whether it is object-safe (no generic methods)

If object-safe, prefer Option A (no macro, cleaner). Otherwise use Option B.
