# Task 21.4 — Fix Silent Data Truncation and Lossy Conversions

## Severity

**MEDIUM-HIGH** — Silent data corruption.

## Problem

Three locations silently lose or corrupt data without any error or warning:

### 1. `bind.rs:29-30` — `u64` → `i64` truncation

```rust
Value::BigUnsigned(v) => {
    let _ = args.add(v.map(|u| i64::try_from(u).unwrap_or(i64::MAX)));
}
```

A `u64` value like `18_446_744_073_709_551_615` silently becomes `9_223_372_036_854_775_807`.
Same issue at `bind.rs:109` for Postgres.

### 2. `value.rs:68` — `Decimal` → `f64` precision loss

```rust
OrmpiValue::Decimal(d) => sea_query::Value::Double(Some(
    d.to_f64().unwrap_or(f64::NAN),
)),
```

`Decimal("123456789.123456789")` loses precision in `f64`. Values that don't fit become `NaN`.

### 3. `value.rs:53` — `Null` encoded as `Int(None)`

```rust
OrmpiValue::Null => sea_query::Value::Int(None),
```

Semantically wrong: null is not an integer-null. Some backends or query builders may
interpret this differently.

### 4. `model/executor.rs:131` — Postgres RETURNING PK defaults to 0

```rust
let id: i64 = row.try_get(model_def.pk_field.as_str()).unwrap_or_default();
```

If the column name is wrong or the type doesn't match, silently returns `0` as the PK.

## Fix

### Fix 1 — `u64` → `i64`: Return error on overflow

```rust
Value::BigUnsigned(v) => {
    let val = v.map(|u| {
        i64::try_from(u).map_err(|_| {
            // Log or propagate — value too large for signed integer column
            i64::MAX // as last resort, but warn
        })
    });
    // Option<Result<i64, _>> → need to handle properly
}
```

Since `bind_sqlite` returns no `Result`, change the signature to return `Result`:

```rust
fn bind_sqlite(args: &mut SqliteArguments<'static>, value: Value) -> crate::Result<()> {
    // ...
    Value::BigUnsigned(v) => {
        if let Some(u) = v {
            let i = i64::try_from(u).map_err(|_| OrmpiError::ValidationError(
                format!("Value {u} exceeds i64 range — BigUnsigned overflow")
            ))?;
            let _ = args.add(i);
        } else {
            let _ = args.add(Option::<i64>::None);
        }
    }
    // ...
}
```

Propagate `Result` through `sqlite_arguments`, `mysql_arguments`, `postgres_arguments`,
and all their callers.

### Fix 2 — `Decimal` → `f64`: Use string representation or error

```rust
OrmpiValue::Decimal(d) => {
    // Prefer to pass as string for backends that support it, or error.
    let f = d.to_f64().ok_or_else(|| OrmpiError::ValidationError(
        format!("Decimal {d} cannot be represented as f64 without precision loss")
    ))?;
    sea_query::Value::Double(Some(f))
}
```

Or store as `String` and let the backend handle conversion:

```rust
OrmpiValue::Decimal(d) => sea_query::Value::String(Some(d.to_string())),
```

### Fix 3 — `Null`: Use a proper null representation

```rust
OrmpiValue::Null => sea_query::Value::Bool(None),
// or add a method that takes the expected column type for context
```

At minimum, document why `Int(None)` is used and verify it works correctly on all backends.

### Fix 4 — Postgres PK: Return error instead of 0

```rust
let id: i64 = row.try_get(model_def.pk_field.as_str())
    .map_err(|e| OrmpiError::FieldError {
        model: model_def.model_name.clone(),
        field: model_def.pk_field.clone(),
        message: format!("Failed to read RETURNING pk: {e}"),
    })?;
```

## Files Changed

| File | Change |
|------|--------|
| `ormpi-core/src/bind.rs` | Return `Result` from bind functions; error on `u64` overflow |
| `ormpi-core/src/value.rs` | Error on `Decimal` → `f64` precision loss; fix `Null` encoding |
| `ormpi-core/src/model/executor.rs` | Error on Postgres PK read failure |
| Callers of `sqlite_arguments`, `mysql_arguments`, `postgres_arguments` | Propagate new `Result` |

## Acceptance Criteria

- [ ] `u64` values exceeding `i64::MAX` produce a clear error, not silent truncation
- [ ] `Decimal` values that lose precision in `f64` conversion produce an error
- [ ] `OrmpiValue::Null` is encoded semantically correctly for all backends
- [ ] Postgres RETURNING PK failure is an error, not a silent 0
- [ ] All existing tests pass with updated error handling
