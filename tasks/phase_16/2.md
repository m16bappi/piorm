## Bug 1 — `last()` With Explicit `order_by("pk")` Returns Wrong Row

### Root Cause

`last()` in `queryset.rs` reverses all orderings and sets `LIMIT 1`. The SQL generated is
`ORDER BY pk DESC LIMIT 1`. However, `"pk"` is not a real column — the actual column is
the pk field name (e.g. `"id"`).

The `resolve_column` helper in `evaluate.rs` already handles `"pk"` → real pk column:

```rust
if first == "pk" {
    return model_def.pk_field.clone();
}
```

But `parse_order_spec` in `base.rs` does NOT resolve `"pk"`:

```rust
fn parse_order_spec(s: &str) -> OrderSpec {
    if let Some(stripped) = s.strip_prefix('-') {
        OrderSpec { field: stripped.to_string(), descending: true, ... }
    } else {
        OrderSpec { field: s.to_string(), descending: false, ... }
    }
}
```

`OrderSpec.field` is set to `"pk"` literally. When the SQL ORDER BY clause is built, it
uses `field` directly as the column name, so `ORDER BY pk` is emitted — an unknown column
in most databases.

### Fix — `ormpi-py/src/model/base.rs`, `parse_order_spec`

Map `"pk"` (and `"-pk"`) to the model's actual pk column **at query build time**. The
easiest approach is to resolve `"pk"` later in the SQL-building layer, but since
`parse_order_spec` doesn't have access to the `ModelDef`, the fix should be in the
`order_by` SQL builder in `ormpi-core`:

**File:** `ormpi-core/src/query/evaluate.rs`, wherever `order_by` fields are turned into
SQL `ORDER BY` expressions.

```rust
// When iterating state.order_by to build ORDER BY clause:
for spec in &state.order_by {
    let col = if spec.field == "pk" {
        model_def.pk_field.as_str()
    } else {
        spec.field.as_str()
    };
    // ... build ORDER BY col ASC/DESC
}
```

Verify this path and add the `"pk"` → `model_def.pk_field` substitution everywhere
`spec.field` is used as a column name.

## Bug 2 — `update_or_create` Generates Invalid SQL

### Error

```
RuntimeError: Database error: near "WHERE": syntax error
```

Occurs in `test_empty_defaults_just_creates` which calls:

```python
obj, created = await Author.objects.update_or_create(
    name="Alice", email="alice@test.com"
)
```

### Root Cause

`update_or_create` in `queryset.rs` builds an UPDATE statement that produces something
like:

```sql
UPDATE authors SET  WHERE name = 'Alice' AND email = 'alice@test.com'
```

An empty `SET` clause is emitted when `defaults=None` or `defaults={}` is passed, because
the code tries to build `SET <defaults>` but there are no default values. This is a SQL
syntax error.

The correct behaviour when `defaults` is empty: do a `get_or_create` with no updates —
i.e. look up the row, return it if found, create it if not.

### Fix — `ormpi-py/src/query/queryset.rs`, `update_or_create`

```rust
fn update_or_create(...) {
    // If defaults is None or empty, delegate to get_or_create
    let has_defaults = defaults
        .map(|d| !d.is_empty())
        .unwrap_or(false);

    if !has_defaults {
        return self.get_or_create(py, None, kwargs);  // re-use existing logic
    }

    // ... existing update logic for non-empty defaults
}
```
